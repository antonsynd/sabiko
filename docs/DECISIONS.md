whether it is a one-way or two-way door. Dates are when the owner settled them.

| 52 | 2026-10-29 | Tuples and `()` values (#6). A tuple whose elements hold no reference is a `System.ValueTuple` instantiation, exactly C#'s for the same tuple: up to seven elements directly (arities 1 to 7), more nested in `Rest` (the eight-parameter instantiation holds elements 1 to 7 and a tuple of the rest, so `t.7` is `t.Rest.Item1` and `t.15` is `t.Rest.Rest.Item2`). A tuple with a reference anywhere among its elements (`&T`, `&mut T`, `&str`, or a tuple holding one) is a `ref struct` generated into the module (`IsByRefLikeAttribute`), named after the Sabiko type (`'(&mut i64, &i64)'`), with fields `Item1`..`ItemN` (no `Rest`) and a constructor taking the elements in order. A `()` value is never loaded or stored (it is stateless: a write is dropped, a read pushes nothing), and where the IL needs one (a call argument, a constructor argument) a zero-initialised `Unit` local is loaded; `-> ()` stays `void` and locals of type `()` still get no storage (decision 32). Supersedes the `()` part of decision 35 | ValueTuple is what C# itself uses, so C# sees `(int, bool)` parameters and returns with no glue, and the IL for literals and element access is byte for byte what Roslyn emits; it is a plain value type with public fields (no indirection, no allocation), which the JIT promotes like any small struct. The empty struct is the smallest storage C# can name for `()` and makes `()` fields and parameters ordinary | Rules out, for now: C# sees a compiler-named `ref struct` (not a ValueTuple) for a tuple holding a reference, which C# cannot use as a generic argument either, and two Sabiko assemblies have distinct types for the same such tuple; such tuples cannot be struct fields (references in fields wait for lifetimes, Phase 9). `System.ValueTuple` of arity 2 to 8 is `LayoutKind.Auto` (arity 1 is sequential), so a struct with a tuple field is laid out automatically by the CLR, as the equivalent C# struct is: no fixed field order for native interop. | 53 | 2026-10-29 | Methods (#7). An inherent `impl` block is allowed for a struct of the file only (E0211 otherwise, rustc's E0390); its members are functions, with an optional first `self`, `mut self`, `&self` or `&mut self`. They are definitions outside the item namespace, named `Type::Name` (exactly two segments; `Self::Name` and `Self` inside the block) or called with method syntax; fields and methods are separate namespaces. A method call finds its method as rustc's probe does for inherent impls: the receiver is dereferenced step by step and each step is matched by value, then by `&`, then by `&mut` (a reference matched by value is reborrowed); a path call (`P::Get(p)`) adjusts nothing. The output lifetime of a `&self`/`&mut self` method is `self`'s whatever its other reference parameters. Lowering: every function of an impl block is a `public static` method of the struct's own value type, the receiver its first parameter, lowered like any parameter by decision 32 (`&self` an `in P&` with `IsReadOnlyAttribute`, `&mut self` a `ref P&`, `self` a `P` by value); a call is a direct `call 'P'::'Name'(..)`. Instance methods were the alternative: C# would write `p.Get()`, but a `&self` method would need a `readonly` instance method, a `&mut self` method a mutable one, and a by-value `self` has no instance form at all (it would need a copy and a call by reference, or a static method anyway); the probe and the borrow rules would be the same, only the IL shape would differ. | 54 | 2026-10-29 | Two-phase borrows (#15), as rustc has them. MIR borrows carry a `BorrowKind` (`Shared`, `Mut { two_phase }`); exactly two borrows are two-phase, both implicit `&mut` borrows made for a call: an autoref'd `&mut self` receiver and the reborrow `&mut *m` of a `&mut` argument passed where a `&mut` is expected (decision 25's coercion site, at call arguments only); explicit `&mut` expressions never are. A two-phase borrow goes into a temporary that exactly one call reads (the validator checks it). The loan facts treat it as *reserved* from its creation to that call, its *activation*, by rustc's dominance test (dominated by the reservation's successor, not by the activation): the reservation is an access that conflicts with every other mutable loan, reserved or active, but not with shared loans; while reserved the loan tolerates reads and shared borrows of its place and nothing else (writes, moves, mutable borrows and reservations conflict); the activation is a mutable borrow of the place checked against every other live loan. An activation that conflicts with a loan its reservation already conflicted with is not reported again | Seven rules confirmed with rustc (posted on #15) separate what two-phase borrows allow from what they do not (`v.Add(v.Get())` and `Use(m, m.X)` are accepted, `P::Add(&mut v, v.Get())`, `v.Add(v.Bump())`, `v.AddFrom(&v)` are not, a shared borrow taken before the reservation is fine while it is dead at the call); expressing them in the existing facts keeps MIR's evaluation order (decision 36) and the Polonius engine (decision 23), which has no two-phase notion of its own. Delaying the borrow in MIR to the call was the alternative: it would change when the receiver place is evaluated and would accept programs rustc rejects (a shared borrow live at the call) | Matches Rust; one-way in practice (which programs compile) |
